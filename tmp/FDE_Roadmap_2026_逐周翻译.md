# FDE Roadmap 2026：按周翻译（只翻 Topic 和 Assignment）

原文是 Codebasics 的《Forward Deployed AI Engineer Roadmap 2026》。下面只翻译每周要学什么（Topic）和每周要交什么作业（Assignment），用大白话写。原文里每节给的学习资源链接、后面的 12 条原则、工具表、案例，这次没翻。

一个说明：原文前面的总表和正文里，分周的方式不太一致。这里按正文每一节实际的分组来，不另外改分组。

## 先决条件：开始之前要会什么

原文说，至少有 1 年编程经验（任何语言都行），还要会这 5 样：

1. 编程基础：变量、数据类型、循环、条件判断、函数、报错处理、基本的面向对象（类和对象）。
2. SQL 基础：SELECT、WHERE、JOIN、GROUP BY，能看懂一张简单的表结构。做 FDE 要经常去企业数据库里拉数据、看数据。
3. Git 和 GitHub：clone、commit、push、分支、提 pull request。
4. 互联网是怎么回事：HTTP 请求和返回是什么、JSON 长什么样、API 大概是干什么的。
5. 会排错：能看懂报错信息，会用打印和日志一步步找问题，会查文档，不轻易放弃。

## 第 1–2 周：给企业 AI 写 Python——FastAPI、Pydantic、异步

### 要学什么

- Python 基础：for 循环、数据类型、变量、if else。
- FastAPI：怎么定接口路由、怎么用 Pydantic 定请求和返回的数据格式、后台任务、中间件。
- 用 Pydantic 做数据校验：怎么定数据格式、怎么写自定义校验规则、嵌套模型怎么写。
- 报错处理的花样：HTTPException、自定义报错处理、返回格式统一的报错信息。
- 环境管理：用 .env 文件管配置、管密钥，密钥绝不能写死在代码里。
- 在 Python 里调大模型（比如用 Groq 这类服务）。

### 作业

- [ ] 做一个工单跟踪的 FastAPI 服务，4 个接口：新建工单、列出全部工单、改工单状态、按 ID 查工单。用 Pydantic 模型校验请求和返回的数据，报错处理要规范（HTTPException、格式统一的报错返回）。
- [ ] 再加一个 /summarize 接口，调大模型（Groq 免费层）给工单描述做摘要。API 密钥从 .env 里读，绝不写死。
- [ ] 把项目推到 GitHub，写个 README 说清楚怎么跑起来。

## 第 3 周：Vibe Coding（用 AI 写代码）

### 要学什么

- 用 AI 写代码能快很多，但代码是你负责，不是 AI 负责。AI 会编造、会出错，所以一定要有测试兜底，不能直接把 AI 写的东西推上生产。
- 有公司会用 Aikido 这类平台，给开发人员和 AI 写出来的东西加一道安全检查。
- 工具选一个，钻深：Claude Code、Cursor、GitHub Copilot、Antigravity。
- Claude Skills、CLAUDE.md、上下文管理。
- 先写规格再动手：SDD（方案设计）→ 执行计划 → 一步步做。可以这样跟 Cursor 说：“尽可能多提问。”
- 检查 AI 生成的代码：逐行看改动，抓住编造出来的接口、漏掉的边界情况、薄弱的报错处理、写死的密钥。这是现在面试也会考的本事。

### 作业

- [ ] 用 Claude Code 或 Cursor，给第 1–2 周的工单系统加功能：先写一个 CLAUDE.md，定 5 条项目规矩（命名、报错处理、文件夹结构、类型标注、不写死密钥），再让 AI 加 2 个新功能——分配维修人员、加一个带校验的优先级字段。
- [ ] 练代码审查：让 AI 生成大约 100 行新功能的代码，然后不靠 AI，自己找出并修掉至少 3 个问题（编造的接口、漏掉的边界情况、薄弱的报错处理）。

## 第 4–5 周：大模型基础和 RAG

原文说，在他们公司 30% 到 40% 的项目都要用到某种 RAG（检索增强生成），整个行业也差不多。学 RAG 之前，先把大模型基础搞清楚。

### 要学什么

- AI 的大版图：机器学习、深度学习、生成式 AI、Agent AI，各是什么。
- Transformer 结构，大模型是怎么工作的。
- 大模型核心概念：temperature、top-p、top-k、上下文窗口、自回归生成。
- RAG、切分策略、有向量库的 RAG 和不用向量库的 RAG。
- 数据灌入流程：PDF、Word 制度文件、Excel 导出 → 切块（固定切、递归切、语义切）→ 转成向量。
- 向量数据库：至少会用一个，比如 ChromaDB、Qdrant、Pinecone、PgVector。
- 检索质量：语义检索、关键词检索（BM25）、混合检索、重排序。
- 防胡说八道的护栏： grounded（有据可依）、带引用、答不出就说不知道。
- 时刻想着成本和延迟：多试几个模型（开源的、商业的都试），选最便宜、延迟又够用的那个。
- 有些环节用开源模型（比如 Hugging Face 上的）往往能省不少钱。

### 作业

- [ ] 拿 10 份真实 PDF（设备手册、人事制度、供应商合同都行）做一套 RAG：灌入 → 切块 → 转向量 → 回答问题时带上出处页码。
- [ ] 把这个 RAG 项目写成 Kaggle 笔记本或 GitHub 仓库，分享到 LinkedIn 上。

## 第 6–8 周：Agent AI、多 Agent 系统、MCP

### 要学什么

- Agent 到底是什么：ReAct 循环（想一想、动一动、看结果，再循环）。
- 工具调用：给工具定清楚的格式和边界、输出结构化的 JSON。
- 用 LangChain 做一个 Agent。
- 用 LangChain 做一个购物 Agent。
- 用 LangGraph 做多 Agent 系统。
- LangGraph：状态、节点、条件边、记忆持久化。
- 多模态 Agent。
- 人在回路：Agent 信心不足、或者动作不可撤销时，先停下来，转给人处理。
- MCP（Model Context Protocol）：把企业工具暴露给 Agent 的标准办法。
- 护栏和评测：限制 Agent 能干什么，上线前先测好， 别等客户先发现问题。

### 作业

- [ ] 在第 1 周的工单系统上，做一个工单分派 Agent：读进来的报修，先用 RAG 查设备手册，定优先级，再通过你的接口新建工单，全程用工具调用完成。
- [ ] 加人在回路的中断：如果 Agent 的信心低于 85%，或者优先级是 P1，就不要自动建单，转到“待人工复核”状态。
- [ ] 录一个 5 分钟演示视频，像给客户 IT 团队讲一样，说清楚 Agent 是怎么做决定的，发到 LinkedIn 上。
- [ ] 做一个 3 个 Agent 的 LangGraph 系统：1 号 Agent 从 RFQ（询价单）/供应商文件里抽关键字段，2 号 Agent 对照批准供应商名单校验完整性，3 号 Agent 起草采购建议，发到一个模拟审批接口。

原文这节还补了一句做事的态度：你不是在做演示，你是在给客户环境里写要长期跑的生产代码，数据又乱、IT 安全规矩又多、用的人又不懂技术。所以要写得稳妥，文档要写全。

## 第 9 周：ERP 和企业数据对接

### 要学什么

- 很多 FDE 岗位的头衔就叫“FDE / 对接工程师”。你要给 ERP 上面搭一层对接层，让 AI 能用上 ERP 里的数据。有 SaaS 公司专门把这层对接做成产品；客户要没买这类产品，这层就得你来搭。
- ERP 大版图：SAP、Oracle NetSuite、微软 Dynamics、Tally。什么叫“记录系统”，主数据和交易数据有什么区别。
- SAP 各模块大概管什么（PM、CS、MM、SD、HR），知道个大概就行，不用钻深。
- 数据怎么拿出来：现成连接器（Palantir Foundry、Databricks、Airbyte）、OData/REST 接口、MCP 服务。
- SAP OData 实操：用免费沙箱调 S/4HANA 的接口（设备主数据、工单），不用装 SAP。
- 企业级 REST 接口设计：认证（OAuth2、API 密钥）、限流、重试、幂等（重复调用不会重复生效）。
- 数据质量的现实：重复的主数据、看不懂的代码要查对照表、过期数据。
- 一项稀缺本事：知道该向客户 IT 团队要什么——数据字典、接口目录、授权、沙箱权限。

### 作业

- [ ] 调 SAP Business Accelerator Hub 免费公开沙箱里的设备主数据 OData 接口（API_EQUIPMENT），拿到设备详情，包括功能位置和维护工厂。不用装 SAP、不用许可证，注册个免费账号，在接口页面点“Show API Key”拿密钥就能调。
- [ ] 写一个 Python FastAPI 接口，把上面这个调用包一层，返回结构化 JSON（设备状态、上次维护日期、分配的维修人员），再把它接成你 Agent 的一个工具。
- [ ] 写一页对接说明（来源系统、接口、认证方式、字段、刷新频率），写得像要交给客户 IT 团队审的那种。

## 第 10–11 周：AI 的 DevOps——Docker、Kubernetes、CI/CD

### 要学什么

- 做 FDE，你要负责 AI 那层背后的基础设施，还要负责持续交付。做法有章法、文档能复用，能帮所有人省时间、少踩坑。
- Docker：多阶段构建、容器仓库（AWS ECR、Azure ACR）、给 AI 应用瘦身镜像。
- Kubernetes：部署、服务、配置项、密钥、资源上限、存活和就绪探针。
- 用 GitHub Actions 做 CI/CD：检查代码 → 跑测试 → 构建 → 推送 → 部署，一条流水线走完。
- API 网关的花样：限流、认证（OAuth2/JWT）、CORS、请求路由。
- 基础设施即代码：Terraform 基础，用来配云资源。
- 密钥管理：AWS Secrets Manager、Azure Key Vault，密钥绝不放环境变量里。
- A/B 测试和金丝雀发布：给不同模型版本放量。
- 本地部署的 Kubernetes：kubeadm、Rancher、离线 Docker 仓库、私有大模型托管（Ollama、vLLM）。

### 作业

- [ ] 把第 4–6 周的多 Agent 系统用 Docker 打包，推到 Docker Hub 或 AWS ECR。
- [ ] 写一个 GitHub Actions 工作流，推到 main 分支就自动跑测试、自动部署。
- [ ] 部署到一台云虚拟机或云容器服务（AWS ECS、Azure Container Apps），把能访问的链接分享出来。

## 第 12–13 周：LLMOps——可观测、评测、安全

### 要学什么

- 大模型调用链路日志：每次请求记下输入、输出、延迟、用的 token 数（LangSmith、LangFuse、OpenTelemetry）。
- 用 Prometheus + Grafana 做指标看板：每分钟请求数、P95 延迟、报错率、每天 token 花费。
- 上线后的评测：回归测试集、幻觉率监控、跟标准答案对比。
- 成本管理：token 预算、模型路由（简单的活走小模型，只有真要精度的才走贵的模型）、报警阈值。
- 安全：OWASP 大模型 Top 10——提示词注入、数据泄露、输出处理不安全。
- RBAC（权限分级）和单点登录：多租户 AI 应用的权限层，OAuth2 / SAML / Azure AD 的对接方式。
- 扩容和可靠性：按负载自动扩缩容、用 Locust 做压测、定 SLA。

### 作业

- [ ] 给你的 AI Agent 接上 LangSmith 或 LangFuse，抓 50 条不同类型工单的测试链路。
- [ ] 搭一个 Grafana 看板，至少有：每分钟请求数、P95 延迟、报错率、每天 token 花费。
- [ ] 给你的 AI 系统写一份安全威胁模型：找出 3 个提示词注入风险，写清楚怎么防。
- [ ] 用 Locust 压测你的接口，50 个并发用户，记录结果。

## 第 14–16 周：企业 AI 的系统设计——HLD 和 LLD

### 要学什么

- 先搞懂客户现在的系统是怎么设计的，再建议你的对接层怎么加进去，别把人家现有的用法搞坏。
- AI 系统设计为什么不一样：大模型不确定、贵、慢、还一本正经地答错。架构里很多不寻常的设计，都是为了防这四点中的某一点，要能说出每个设计防的是哪一点。
- 模型层：调接口的模型和自己部署的模型怎么选、模型路由怎么定。小模型做抽取和分类，只有真要综合判断才用最强的模型。这是省钱最大的一招。
- 检索层：灌入路径和查询路径、混合检索（向量 + 关键词）、重排序、切分策略、元数据过滤。RAG 答得差，十次里有八次是检索的问题，先查检索，别怪模型。
- 编排：工具调用、想—做—看的循环、可靠性的数学——每步 95% 准，10 步下来整体只有 60% 左右。企业里流程固定的事，优先用固定流程；只有真开放的任务才用开放式 Agent。
- 延迟和成本设计：首 token 时间和总时间、流式输出、缓存阶梯（先查完全一样的回答缓存，再查语义缓存，再查固定提示词前缀），还有输出上限和提示词卫生。成本是设计出来的，不是月底看账单才发现的。
- 信任层：输入和输出护栏、评测就是 AI 系统的单元测试（没有评测就不许上线）、端到端链路追踪，能分清是检索坏了还是生成坏了。
- 降级和兜底设计：主模型 → 备用模型 → 体面地转人工，每一级都要告诉用户，别悄悄失败。指望不出事不是架构。
- HLD（高层设计）：有哪些组件、组件之间怎么协作、技术栈选了什么、为什么选、接受了什么取舍、部署拓扑（云还是本地、怎么连 ERP）、非功能要求（企业 AI 要的是可靠、数据不出境、成本可控，不是要扛几百万用户）。
- LLD（底层设计）：接口规格（OpenAPI/Swagger）、请求和返回的约定、数据库表结构（实体、关系）、时序图——不光画顺利的流程，出错的流程也要画。
- AI 系统的 LLD：Agent 和工具的边界、每个不可撤销的动作前面都要有一道确定性关卡、模型和提示词配置、哪些是配置、哪些是代码，要划清楚。
- 架构决策记录（ADR）：定了什么、否掉了哪些备选、代价是什么。画图工具：draw.io（免费）、Eraser.io、Mermaid，留住图的源文件，不光留一张图。

### 作业

- [ ] 写一个 AI 现场服务管理系统的 HLD（也就是一份 SDD 里的高层部分）：架构图、组件清单、技术栈及选型理由和取舍、部署拓扑（云还是本地、怎么连 ERP）、模型路由策略，再写一条模型托管方式的架构决策记录。
- [ ] 给同一个系统写 LLD：接口表（至少 8 个接口，带请求和返回模型）、数据库表结构（设备、工单、维修人员、SLA 策略）、工单创建的时序图，再画一张 ERP 写入失败时会发生什么的时序图。
- [ ] 像面试一样，5 分钟口头讲清楚你的设计，录下来自己复盘，把架构图发到 LinkedIn 上。

## 第二阶段：产品管理和软技能（第 13–24 周）

第一阶段教你把企业 AI 做出来、上线。第二阶段教你去客户现场干活：找到真问题、写清楚、管好人、把上线落地。

## 第 17 周：发现问题和用户调研

原文打了个比方：FDE 像个沉稳的医生。病人说头疼，沉稳的医生不会马上开止疼药，而是先问、先查，找到根因。根因可能是胃胀气引起的头疼，先找到根因再开药。FDE 也一样，先找到根因再动手建东西。

### 要学什么

- 5 Whys（连问 5 个为什么）找根因、《妈妈测试》（The Mom Test）里的提问办法。
- 访谈和跟岗：一步步画出用户现在是怎么做事的。
- 用户调研基础：用户画像、待办任务（jobs-to-be-done）、买单的老板要什么和一线用户要什么，不是一回事。
- 把“用户嘴上说的需求”和“真正的问题”分开——永远先问“成功长什么样？”
- 调研前要先要到的材料：制度文件、组织架构图、现在的流程指标。
- 访谈框架：用开放式问题挖出真痛点。
- 开调研会：议程、会场规矩、怎么记产出。
- 把问题量化：出错率、手工花的时间、SLA 违约次数、每次出错的成本。
- 调研时怎么管范围蔓延；保密协议、数据治理、现场准入规矩。

### 作业

- [ ] 挑一个你真了解的流程（家里生意、你工作的地方都行），写一份调研访谈提纲，10 个开放式问题。
- [ ] 真去访谈一个天天做这个流程的人，记下现在的步骤、痛点，量化出来：手工花了多少小时、出错率多少、每次出错多少钱。
- [ ] 写一页问题陈述，把业务影响量化，让受访者确认写得准不准。

## 第 18 周：用泳道图画现在的流程（AS-IS）

### 要学什么

- BPMN（业务流程建模符号）基础：池、泳道、事件、网关、任务、连接线。
- 画 AS-IS（现在是什么样）的流程图，把手工步骤画准。
- 找哪些步骤适合自动化：重复的、有规则的、量大的、容易出错的。
- 跟相关方一起定 TO-BE（将来 AI 自动化之后是什么样）。
- 工具：draw.io（免费）、Miro（免费版）、Eraser.io。

### 作业

- [ ] 给上一周调研的流程，画一张完整的 AS-IS 泳道图。
- [ ] 把你想用 AI 自动化的步骤标成橙色，写清楚为什么选这些步骤。
- [ ] 把图发到 LinkedIn 上，配一段文字说你学到了什么。

## 第 19 周：业务需求文档（BRD）怎么写

### 要学什么

- BRD 结构：摘要、范围和范围外、AS-IS/TO-BE、功能需求、对接需求、数据需求、验收标准、风险和假设。
- 验收标准要能量化：不说“系统要快”，要说“工单分派在 P95 下不超过 5 秒”。
- 管范围：哪些不做、为什么不做。
- BRD 版本管理和变更记录。
- 常见毛病：需求写得含糊、漏了排除项、验收标准没法测。

### 作业

- [ ] 给你调研的那个流程写一份完整 BRD，至少 8 个部分，功能需求表里至少 10 条需求。
- [ ] 找同行看一遍：每条需求有没有能量化的验收标准？
- [ ] 把 BRD 摘要做成 LinkedIn 轮播图或文章发出来。

## 第 20 周：技术设计文档（TDD）

BRD 说的是“要什么、为什么”。TDD 是告诉开发人员（或 AI 写代码的 Agent）系统具体该怎么表现。

### 要学什么

- TDD 和 BRD 的区别；怎么从 BRD 推出功能流程和数据流程。
- 字段级校验规格：哪些字段必填、格式允不允许、容差阈值。
- 业务规则规格：比如 SLA 升级——到 SLA 时长的 80% 先警告，到 100% 自动升级。
- 出错场景和异常处理要求。
- 对接规格：来源系统、接口、认证、刷新频率。

### 作业

- [ ] 从你前面写的 BRD 推出一份 TDD：功能流程、校验规则、异常处理、对接规格都要有。
- [ ] 写一条业务规则规格（流程图 + 规则表），写得像要交给开发人员的那种，然后喂给一个 AI 写代码 Agent，看它能不能照着建对。这才是检验规格写得清不清楚的真办法。

## 第 21–22 周：相关方管理和沟通

### 要学什么

- 相关方有哪些：最终用户、流程负责人、IT 把关人、出钱的老板。按影响力和关注度画一张图。
- 管预期：怎么体面地说不、怎么拿范围换时间、怎么把谈好的事落到文字上。
- 沟通节奏：会议议程、会议纪要、每周进展、升级路径。
- 给高管汇报：3 页幻灯片的格式（问题、方案、结果）。
- 给不懂技术的人演示：展示结果，不展示架构。
- 用客户当地语言沟通：客户内部常用印地语或当地方言时，要能听懂、能回应。
- 在不确定的时候也要稳：用权威的语气问清楚——“帮我理解一下，你说的是 X 还是 Y？”

- 关注几个人：Colin Jarvis（OpenAI）、Joe Schmidt（a16z）、Dhaval Patel（Codebasics）、Andrej Karpathy。

- 在 LinkedIn 或 Discord 上帮 5 个问 FDE 问题的人。

### 作业

- [ ] 写 300 字短文：“FDE 能解决什么问题，是解决方案工程师解决不了的？”
- [ ] 录一个 5 分钟、3 页幻灯片的高管汇报，讲你第一阶段的项目（问题、方案、结果），发到 LinkedIn 上。
- [ ] 找个朋友扮难缠的流程负责人，开一次模拟相关方会议，练怎么顶住范围扩张，记一份会议纪要。

## 第 23 周：UAT 和上线

### 要学什么

- UAT 和 QA 测试的区别：UAT 能验证什么，是单元测试验证不了的。
- 写 UAT 测试脚本：场景、前置条件、测试步骤、预期结果和实际结果、通过还是不通过。
- UAT 的进入和退出标准：开始 UAT 之前必须满足什么、批准上线之前必须满足什么。
- 带真实最终用户做 UAT：怎么管预期、缺陷怎么分流、严重程度怎么分（严重 / 高 / 中 / 低）。
- 上线检查清单：数据迁移核对过、回滚方案写好、支持联系人列好。
- 上线后重点保障期（hypercare）：升级矩阵、事故响应手册。

### 作业

- [ ] 写一份 15 个场景的 UAT 测试脚本，覆盖 P1 紧急派单、SLA 违约升级、备件缺货、维修人员技能不匹配。
- [ ] 找个朋友扮“业务用户”真跑一遍 UAT，记下发现的缺陷，先修 P1 的。
- [ ] 给你第一阶段的项目写一份上线检查清单，带回滚方案。

## 第 24 周：变更管理、交接、证明 ROI

项目不是系统能跑就完了，是客户团队不用你也能自己用，才算完。

### 要学什么

- 最终用户为什么抗拒 AI 系统，怎么应对——ADKAR 模型。
- 最终用户培训：按角色写指南、录演示视频、写 FAQ。
- KPI 设计：ROI、效率提升、出错减少、SLA 达标率。
- 做 KPI 看板，要让不懂技术的人也能看懂、能信。
- 交接文档包：架构总览、运维手册、联系人表、已知问题。
- 上线后复盘和持续改进的反馈循环。

## 加餐：第 7 个月以后，SAP 深入对接和现场服务领域（不是所有 FDE 岗位都需要）

原文说，这部分不是大多数 FDE 岗位必需的。但如果你瞄准 SAP 很重的咨询公司，或者制造、现场服务的客户，这份深度就是加分项。

### 要学什么

- SAP 对接方式：BAPI、OData、RFC、IDoc、SAP CPI。
- SAP CPI 做中间件：对接流程、消息映射、按内容路由。
- SAP Datasphere：给 AI 用的读数层视图——设备表现、维修人员利用率、SLA 达标历史。
- 写 BAPI 对接目录：函数名、输入输出参数、错误码（比如 BAPI_ALM_ORDER_MAINTAIN 是改工单的）。
- SAP PM（工厂维护）：设备主数据、功能位置、工单、通知单；SAP CS（客户服务）：服务单、服务合同、资源相关计费。
- 备件管理：物料预留、货物发放、库存总览；SLA 管理：响应时间和解决时间、P1–P4 优先级、罚则。
- 现场维修人员排班：按技能派、按地理位置派、看排班表；物联网基础：传感器数据（振动、温度、压力）怎么触发预测性维护工单；保修管理和印度制造合规。
