# 初学者FDE学习之路

## 写在前面的话

FDE现在是一个特别火的名词, 随着AI在企业里更多的使用, 企业也越来越需要能把AI真正用起来的人.

对于程序员或者产品经理来说, 转型FDE是一个值得考虑的方向.

但是, 现在的问题是市面上的很多材料都特别虚, 都没有说在点子上.

本文从一个初学者开始说, 怎么一步一步学习FDE. 这里说的FDE, 主要是做企业AI落地的工程师. 不光要会写代码, 还要能搞清楚客户的问题, 对接现有系统, 把东西部署起来, 最后交给客户使用.

我们不按周安排学习进度, 而是按阶段往下走. 每个阶段都有作业, 都围绕前面开始做的工单系统继续扩展, 不要每学一个新工具就重新开一个项目.

这个系统最开始只需要能记录报修、查询工单、修改状态. 后面再一步一步加上设备手册问答、AI分派、设备数据查询、备件申请、SLA提醒和人工审批. 最后把它部署起来, 让业务用户验收, 再交接给使用和维护的人.

原路线里有一些独立的练习, 我们会把它们放回这个业务里. 比如多Agent不另外做购物助手, 而是处理维修缺备件之后的采购申请; 写需求文档也不重新找一个题目, 就写我们这套工单系统. 这些是逐步增加的学习目标, 不是说第一阶段就要全部做完.

本文参考了 Codebasics 的 [FDE Roadmap 2026 原文](FDE_Roadmap_2026.pdf) 和仓库里的 [逐周翻译](FDE_Roadmap_2026_逐周翻译.md), 按我们的学习方式重新整理, 不是逐字翻译. 文中的工程注意事项和部分练习做了补充.

## 面向谁

这篇文章面向对计算机编程有一定了解, 并且(最好)会使用Claude Code或者Codex的朋友.

简单来说, 最好能手搓, 其次是能vibe coding出来下面的小东西. 但不管用哪种方式, 你都要能看懂代码, 知道出错之后该从哪里查.

1. Python 能写一小段代码, 读文件, 会写循环, 会写if、break、函数, 知道怎么处理报错.
2. SQL 会对表进行增删改查, 会join, 会用GROUP BY做简单统计.
3. Git 能拉代码、能提交, 知道分支和pull request怎么用.
4. 知道HTTP请求和返回是什么, 能看懂JSON, 知道API是干什么的.
5. 遇到问题能看报错、查日志、查文档, 而不是只把报错丢给AI反复重试.

然后照着这里做, [SQLite 数据库指南：从零开始掌握 Python 数据库操作](https://blog.csdn.net/2301_80216352/article/details/155320108).
会用Python对SQLite进行增删改查即可.

原路线建议有至少一年的编程经验. 如果你还没有这么多经验, 也可以开始, 但要给基础部分多留一些时间.

## 第一阶段 学习企业级AI开发用到的Python

从企业AI开发的需求来看, Python是很重要的技能. 但是Python可以学的东西非常多, 你不需要完全学完了Python后才进入第二阶段.

你可以每天花一些时间补基础, 同时尝试用Python + FastAPI来构建一个Web服务器. 先把一个能用的小项目做出来.

总体来说你要学习的东西包括

1. Python基础
    - for循环、数据类型、变量、if else
    - 函数、模块、类和对象
    - 异常处理和日志
    - async/await的基本用法, 知道异步接口里不能随便放阻塞操作
2. FastAPI
    - 接口设计
    - 请求和返回的数据格式
    - 后台任务
    - 中间件
3. Pydantic
    - 确定数据格式
    - 自定义校验规则
    - 嵌套模型
    - 报错处理
4. 环境管理: 本地用.env文件管理配置和密钥, 不要把.env提交到GitHub.
5. 在Python里调LLM API, 处理超时、调用失败和返回格式不符合要求的情况.

### 作业

- 先自己写一个工单跟踪的FastAPI服务, 包含5个接口
    - 新建工单
    - 列出全部工单
    - 改工单状态
    - 按ID查工单
    - /summarize接口, 调大模型给工单做摘要
- 用Pydantic模型校验请求和返回的数据, 报错处理要规范, 使用HTTPException和格式统一的报错返回.
- 工单先存到SQLite里, 重启服务之后数据不能丢.
- 给正常请求、字段不合法、工单不存在、模型调用失败分别写测试.
- 把项目推到GitHub, 写个README, 说清楚怎么安装、配置和运行. 提供不含真实密钥的.env.example.

## 第二阶段 学习Vibe Coding

我们要做FDE, 肯定要熟练掌握怎么用AI写代码. 这个阶段开始学习如何Vibe Coding.

但是, 用AI写代码不是把责任也交给AI. 最后代码是你交付的, 出问题也要你来排查.

1. 选一个工具, 建议是Claude Code或者Codex, 先把一个工具用熟.
2. 模型根据预算和实际效果来选, 不用一开始就追最贵的. 拿同一个任务试一下, 看能不能写对、需要改几次、花多少钱.
3. 学习Skills、项目说明文件和上下文管理. 用Claude Code时, 把项目规矩写到CLAUDE.md里.
4. 和AI编程时养成好习惯, 尽量拆成一步一步让AI来做
    - 先说清楚需求和不做什么
    - 再做方案设计
    - 根据方案设计测试用例
    - 让AI一步一步执行计划
    - 及时检查改动, 验证和测试
5. AI可能出错的地方, 都要自己检查
    - 给自己加戏, 编造需求
    - 调用不存在的接口
    - 报错处理乱写
    - 忽略边界情况和关键处理
    - 把密钥写死在代码里

### 作业

- 用Claude Code或Codex, 给第一阶段的工单系统加功能
    - 先写项目说明文件
    - 给项目增加5个规范, 包括命名、报错处理、文件夹结构、类型标注、不写死密钥
    - 再让AI加2个新功能: 分配维修人员和任务优先级
    - 优先级要有合法值校验, 不能随便填一个字符串就存进去
- review AI的代码: 让AI生成大约100行新功能的代码, 然后不靠AI, 自己检查编造接口、边界情况和报错处理等问题. 目标是找出并修掉至少3个真实问题, 不要为了凑数制造问题.
- 跑完测试再提交代码, 在提交说明里写清楚改了什么.

## 第三阶段 学习大模型基础和RAG

企业里的很多问题, 不是大模型知道得不够多, 而是它根本没看过客户的资料.

比如设备怎么维修、报销有什么规定、合同里写了什么, 这些都需要从企业自己的文档里找. RAG就是先找资料, 再让模型根据资料回答.

1. 了解AI的基本概念
    - 机器学习、深度学习、生成式AI、Agent分别是什么
    - Transformer和大模型生成文字的大致过程
    - token、上下文窗口、temperature、top-p等概念, 具体参数是否支持要看模型接口
2. 文档处理
    - 从PDF、Word、Excel里取数据
    - 固定切分、递归切分、语义切分
    - 保留文档名称、页码等来源信息
3. 向量和检索
    - embedding是干什么的
    - 选一个向量库来用, 比如ChromaDB、Qdrant或者pgvector
    - 了解关键词检索、向量检索、混合检索和重排序
    - 知道不是所有检索任务都一定需要向量库
4. 回答要有依据
    - 回答带引用
    - 找不到资料就说不知道
    - 不要拿模型自己知道的东西冒充企业制度
5. 同时关注回答质量、响应时间和调用成本.

### 作业

- 找10份可以合法使用的PDF, 优先选设备手册, 后面可以继续接到工单系统里.
- 做一个RAG项目: 读取文档 → 切分 → 转向量 → 检索 → 回答, 回答要带文档名称和页码.
- 准备一组问题, 包括能找到答案的、需要跨段查找的、文档里没有答案的, 记录实际回答效果.
- 把代码和运行说明放到GitHub. 不要上传客户的保密文档, 对外展示用公开或脱敏数据.

## 第四阶段 学习Agent、多Agent和MCP

前面的RAG主要负责回答问题. 到这个阶段, 我们开始让AI调用工具做事情.

比如用户说“这台设备坏了”, 系统先查设备手册, 再判断工单优先级, 最后调用接口创建工单. 这就不只是聊天了.

1. Agent的基本工作方式
    - ReAct循环: 思考、调用工具、观察结果, 再决定下一步
    - 工具调用的输入、输出和权限边界
    - 结构化JSON输出和校验
2. 先用LangChain做一个简单Agent, 再学习LangGraph
    - 状态、节点、条件边
    - 状态持久化和中断恢复
    - 多Agent之间怎么传递结果
3. 了解多模态Agent, 比如从设备照片或扫描件中提取信息.
4. 人工复核
    - 信息不足时不要硬做决定
    - 紧急工单和高风险操作先转人工
    - 不可撤销的动作要有明确的审批和权限检查
5. MCP: 用标准方式把工具接给Agent, 但接入MCP不等于自动有了权限控制.
6. 给Agent加限制和评测, 不能让它无限循环、无限调用工具.

### 作业

- 在工单系统上做一个分派Agent
    - 读取报修内容
    - 用第三阶段的RAG查设备手册
    - 判断优先级
    - 通过工具调用你的API创建工单
- 增加“待人工复核”状态. P1紧急工单或信息不足的请求不能直接自动建单.
- 原路线用85%的置信度作为练习阈值. 如果采用这个规则, 要说明分数从哪里来, 不能把模型自报的85%当成真实正确率; 人工复核还要结合字段完整性、检索依据和确定性业务规则.
- 把一个只读的设备查询工具接成MCP工具, 验证参数校验和访问权限.
- 给同一个工单系统增加“维修缺备件”的多Agent流程, 不另开采购项目
    - 1号Agent从工单和备件询价单里提取设备、备件型号、数量等字段
    - 2号Agent通过工具查询模拟库存和批准供应商名单, 检查是否缺字段、供应商是否符合要求
    - 3号Agent起草备件采购建议, 关联原工单ID, 提交到模拟审批接口
    - 采购建议必须人工批准, 练习阶段不真实下单. 提取结果也要经过字段和业务规则校验
    - 记录每一步的状态和结果, 让维修人员能从原工单里看到备件申请进度
- 录一个5分钟演示, 像给客户IT团队讲一样, 说清楚系统什么时候自动处理、什么时候转人工.

## 第五阶段 学习ERP和企业数据对接

企业不会因为你做了一个AI系统, 就把原来的系统全部换掉. 你更多时候是在原来的ERP、数据库和业务系统上面, 加一层AI能力.

这个阶段不用把自己学成SAP顾问, 先学会看接口文档、拿数据、处理脏数据, 知道应该向客户IT团队要什么.

1. 了解ERP是干什么的
    - SAP、Oracle NetSuite、微软Dynamics等
    - 主数据和交易数据有什么区别
    - 哪个系统保存业务数据的权威版本
2. 数据怎么拿出来
    - 现成连接器
    - REST和OData接口
    - 经过授权的数据库查询和MCP工具
3. 企业接口需要考虑什么
    - OAuth2、API Key等认证方式
    - 超时、限流、重试
    - 幂等: 同一个请求重试, 不能重复创建工单
4. 数据质量
    - 同一台设备有重复记录
    - 状态代码需要查对照表
    - 数据过期、字段缺失
5. 向客户要数据字典、接口目录、权限说明和沙箱账号, 不要一上来就直接操作生产环境.

### 作业

- 尝试调用SAP Business Accelerator Hub的API_EQUIPMENT沙箱, 查询设备信息, 例如功能位置和维护工厂. 沙箱是否开放、需要什么账号和权限, 以当前平台说明为准.
- 没有可用沙箱时, 先用模拟接口练习, 在文档里明确写出哪些数据是模拟的.
- 用FastAPI封装设备查询接口, 返回结构化JSON, 再接成Agent的一个工具.
- 对照接口文档逐一确认字段. 上次维护日期、分配的维修人员等字段如果不在设备接口里, 要找对应数据源, 不能自己编出来.
- 写一页对接说明, 包括来源系统、接口、认证方式、字段映射、刷新频率和失败处理.

## 第六阶段 学习部署和持续交付

本地能跑, 不等于客户能用. FDE还要知道怎么把系统部署出去, 怎么更新, 出问题之后怎么退回来.

先学会把一个服务稳定部署起来, 再补Kubernetes和更复杂的基础设施, 不用一上来就堆工具.

1. Docker
    - Dockerfile、多阶段构建
    - 容器镜像和镜像仓库
    - 数据持久化, 不要容器一删工单就没了
2. GitHub Actions
    - 检查代码 → 跑测试 → 构建镜像 → 推送 → 部署
    - 区分测试环境和生产环境
3. Kubernetes基础
    - Deployment、Service、ConfigMap、Secret
    - 资源限制、存活探针和就绪探针
4. API网关: 认证、限流、CORS和请求路由.
5. 配置和密钥管理
    - 本地开发可以用.env
    - 生产环境优先用专门的密钥管理服务, 按平台安全机制注入或读取
    - 密钥不能写进代码、镜像、日志和公开的流水线配置
6. 了解Terraform、灰度发布和回滚.
7. 了解客户内网部署, 包括离线镜像仓库和私有模型服务, 比如Ollama、vLLM.

### 作业

- 把前面的工单Agent系统用Docker打包, 推到适合项目可见性的镜像仓库.
- 写一个GitHub Actions工作流, 推送到main后自动测试并部署到测试环境.
- 部署到一台云虚拟机或者云容器服务, 配置认证, 用演示数据验证完整流程.
- 写清楚启动方式、配置项、数据存放位置和回滚步骤, 实际回滚一次.

## 第七阶段 学习AI系统的监控、评测和安全

系统上线之后, 你要能回答几个问题: 今天错了多少次? 哪一步慢? 花了多少钱? 换了提示词之后, 是更好了还是更差了?

这些问题不能只靠“我试了一下, 感觉还行”.

1. 调用链路追踪
    - 选择LangSmith或Langfuse, 了解OpenTelemetry
    - 记录模型调用、检索和工具调用的耗时、结果和token用量
    - 日志里的个人信息和业务敏感信息要脱敏, 外部追踪平台要经过数据合规确认
2. 指标监控
    - 每分钟请求数、P95延迟、报错率
    - 每天的模型调用费用
    - P95延迟就是95%的请求耗时不超过这个值
3. 评测
    - 准备固定测试集和预期结果
    - 区分检索错误、回答错误和工具执行错误
    - 每次换模型、提示词或检索策略, 都重新跑一遍
4. 成本管理: token预算、模型路由、超额告警.
5. 安全
    - 提示词注入、数据泄露、不安全的输出处理
    - RBAC角色权限、单点登录和租户隔离
    - 权限检查放在后端和工具里, 不能只靠提示词要求模型遵守
6. 可靠性: 超时、降级、负载测试和服务目标.

### 作业

- 给Agent接上追踪工具, 收集至少50条不同类型工单的测试链路.
- 用Prometheus + Grafana做监控, 至少记录请求数、P95延迟、报错率和每天模型费用.
- 建一个回归测试集, 保存基线结果, 修改一次提示词后比较变化.
- 写一份安全威胁分析, 找出3个提示词注入风险, 写清楚防护办法和验证方式.
- 在自己控制且允许压测的测试环境里, 用Locust模拟50个并发用户, 记录结果. 模型和ERP调用可以先用模拟服务, 不要直接压第三方接口.

## 第八阶段 学习企业AI系统设计

到这里你已经做过接口、RAG、Agent、对接和部署. 现在要退后一步, 想清楚这些东西为什么要这样组合.

系统设计不是把工具名字画进几个框里. 你要能解释, 为什么选这个方案, 它有什么代价, 出错之后怎么办.

1. 先了解客户现有系统, 不要为了加AI破坏原来的业务流程.
2. 模型层
    - API模型和自己部署怎么选
    - 简单分类、抽取用小模型, 复杂任务再考虑更强的模型
3. 检索层: 文档更新、混合检索、重排序、元数据过滤和访问权限.
4. 编排层: 固定流程优先用确定性的工作流, 真正开放的任务再考虑开放式Agent.
5. 延迟和成本: 流式输出、缓存、输出长度限制, 缓存也要区分用户权限和数据版本.
6. 失败处理: 主模型失败怎么办, ERP写入失败怎么办, 什么时候转人工.
7. HLD, 也就是高层设计
    - 系统有哪些组件, 怎么协作
    - 技术选型和取舍
    - 云端还是内网部署
    - 可靠性、数据存放要求和成本目标
8. LLD, 也就是详细设计
    - 接口、请求和返回格式
    - 数据库表和关联关系
    - 正常流程与异常流程的时序图
    - Agent权限、工具边界和人工审批点
9. 架构决策记录: 选了什么、没选什么、为什么, 把理由留下来.

### 作业

- 给工单系统写一份HLD, 包括架构图、组件清单、技术选型、部署方式、模型路由策略.
- 写一条模型托管方式的架构决策记录, 比较调用API和自己部署的取舍.
- 给同一个系统写LLD
    - 至少8个接口, 带请求和返回模型
    - 设备、工单、维修人员、SLA策略的表结构
    - 创建工单的时序图
    - ERP写入失败时的时序图, 说明怎么避免重复写入和状态不一致
- 保留图的源文件, 录一个5分钟的设计讲解, 自己回看能不能讲清楚.

## 第九阶段 学习发现问题和用户调研

前面主要在练怎么把东西做出来. 但到客户现场, 第一件事不是写代码, 而是搞清楚到底有什么问题.

这部分放在后面是为了先用项目建立技术基础. 真正做客户项目时, 调研应该在设计和开发之前开始.

客户说“我们要一个AI助手”, 这还不是一个可以直接开发的需求. 你得继续问, 是哪件事做得慢? 谁在做? 一天做多少次? 做错了有什么影响?

1. 用5 Whys追问根因, 学习《妈妈测试》里的提问方法.
2. 访谈真正做事的人, 有条件就跟着看一遍实际操作.
3. 区分老板想要什么、一线用户需要什么、IT团队允许什么.
4. 调研之前先了解流程制度、组织分工和当前指标.
5. 量化问题: 手工耗时、出错率、SLA违约次数、每次出错的成本.
6. 明确范围、保密要求和数据使用权限, 不要访谈时随口答应所有需求.

### 作业

- 围绕我们做的工单系统, 找一个真实的报修或维修流程, 写10个开放式访谈问题. 可以从公司的IT报修、物业维修或者设备维护入手.
- 访谈一个实际报修、派单或者维修的人, 记录从报修到关闭工单的操作步骤、痛点和能够确认的数据.
- 写一页问题说明, 讲清楚谁遇到什么问题、影响多大、什么结果算成功. 再对照我们已有的功能, 标出哪些解决了真实问题、哪些还需要调整.
- 请受访者确认. 暂时没有数据的地方写“待验证”, 不要为了显得专业编数字. 找不到真实受访者时可以先模拟, 但要明确这是待验证的业务假设.

## 第十阶段 学习梳理业务流程

先把现在怎么做画清楚, 再讨论以后怎么改. 不然你以为省掉的是重复操作, 实际上可能把一个必须的审批步骤也省掉了.

1. AS-IS: 现在的流程是什么样.
2. TO-BE: 改造之后希望是什么样.
3. 学习基本的泳道图和BPMN符号, 表达角色、任务、判断、交接和异常分支.
4. 找出重复、规则明确、数量大、容易出错的步骤, 判断适合普通自动化还是AI.
5. 工具选draw.io、Miro等其中一个就行, 重点是让业务人员看得懂.

### 作业

- 给上一阶段调研的流程画一张AS-IS泳道图, 包括手工步骤和跨部门交接.
- 标出准备自动化的步骤, 逐个写清楚理由, 不要所有地方都塞一个Agent.
- 再画一张TO-BE流程图, 标出人工审批、失败处理和兜底路径.
- 请参与流程的人看一遍, 确认没有漏掉关键步骤.

## 第十一阶段 学习写业务需求文档

需求文档不是越长越好, 而是让客户和开发对“做什么、不做什么、怎么验收”有同一个理解.

这里学习BRD, 也就是业务需求文档.

1. 文档需要说清楚
    - 项目背景和业务目标
    - 范围和范围外
    - 当前流程和目标流程
    - 功能需求
    - 系统对接需求
    - 数据需求
    - 验收标准
    - 风险和假设
2. 验收标准要能测. 不要只写“速度要快”, 可以写“在约定负载下, 工单分派P95延迟不超过5秒”, 并说明测试条件.
3. 需求要有编号, 方便后面对应设计、测试和变更.
4. 管好版本和变更记录, 需求增加了, 时间和成本也要重新确认.

### 作业

- 根据前面的报修流程调研, 给同一个工单系统写一份BRD, 至少8个部分, 功能需求至少10条. 可以覆盖报修、设备查询、手册问答、优先级、人工复核、派单、维修状态、备件申请、SLA提醒和关闭工单, 但最终范围要以调研确认的需求为准.
- 每条功能需求写清楚验收标准, 明确哪些事情本次不做.
- 找一个朋友或同行看一遍, 请对方指出含糊、不能测试或者范围不清楚的地方.
- 用脱敏后的摘要练习对外介绍项目, 不要直接公开客户需求文档.

## 第十二阶段 学习写技术设计文档

BRD说的是要什么、为什么. 技术设计文档要说清楚系统具体怎么表现, 让开发人员或者AI拿到之后能照着做.

这里的TDD指Technical Design Document, 不是测试驱动开发.

1. 从BRD推导功能流程和数据流程, 和前面做的HLD、LLD衔接.
2. 字段级规则: 哪些必填、允许什么格式、字段之间有什么约束.
3. 业务规则: 比如到SLA时长的80%提醒, 到100%升级, 同时说明计时起点和暂停条件.
4. 异常处理: 缺字段、重复请求、接口超时、权限不足分别怎么办.
5. 对接规格: 来源系统、接口、认证、字段映射和刷新频率.
6. 区分代码和配置, 可以配置的规则也要有校验、审批和版本记录.

### 作业

- 根据上一阶段的BRD写一份TDD, 包含功能流程、字段校验、业务规则、异常处理和对接规格.
- 选一条SLA升级规则, 写出流程图和规则表.
- 把这条规格交给AI写代码, 用事先准备的测试用例验证它有没有实现对.
- 如果实现不对, 分清是文档含糊还是代码错误, 不要只靠口头补充需求.
- 按确认后的BRD和TDD补齐工单系统, 不要只写文档不改实现. 重点检查P1人工复核、SLA提醒与升级、备件缺货转申请、维修人员技能匹配这几条流程, 给每条流程加测试, 为后面的用户验收做准备.

## 第十三阶段 学习客户沟通和相关方管理

做FDE不是只和开发沟通. 使用系统的人、负责流程的人、IT团队、出钱的老板, 关注的事情可能完全不一样.

你要能把同一个项目, 用对方听得懂的方式讲清楚.

1. 找出相关方, 了解谁使用、谁审批、谁负责数据和安全、谁决定预算.
2. 管预期: 新需求来了, 说明要增加多少时间, 或者需要拿掉哪些原有范围.
3. 养成会议议程、会议纪要、每周进展和问题升级的习惯.
4. 给管理层讲问题、方案和结果, 不要一上来讲向量库和Agent框架.
5. 给一线用户演示怎么完成任务, 出错了该找谁.
6. 不懂就确认, 可以问“你说的是X还是Y”, 不要假装听懂.
7. 整理公开作品, 用项目记录展示能力, 不用把自己包装成什么都懂的专家.

### 作业

- 写一篇300字左右的短文, 说明你理解的FDE在客户交付中负责什么, 和解决方案工程师等角色有哪些区别和重叠.
- 用3页幻灯片讲清楚项目的问题、方案和结果, 录一个5分钟演示. 未验证的结果要明确标成目标或假设.
- 找朋友扮演不断加需求的流程负责人, 模拟开一次会, 练习说明取舍并记录结论.
- 整理GitHub项目说明, 写3篇学习或项目复盘, 可以分享到LinkedIn或自己常用的平台, 只用可公开的内容.

## 第十四阶段 学习用户验收和上线

开发说“测试通过了”, 不代表业务用户觉得能用. UAT就是让真正使用系统的人, 按实际业务场景验证系统.

1. 区分开发测试和UAT: 一个检查实现是否正确, 一个检查是否满足业务使用和验收要求.
2. UAT脚本要有场景、前置条件、步骤、预期结果、实际结果和是否通过.
3. 明确进入和退出标准: 什么情况下可以开始验收, 什么问题没解决就不能上线.
4. 缺陷分级、负责人和修复安排, 要留下记录.
5. 上线检查: 数据迁移、权限、配置、监控、备份、回滚和支持联系人.
6. 上线后要有重点保障期, 说清楚出问题谁处理、怎么升级.

### 作业

- 给工单系统写15个UAT场景, 包括P1紧急派单、SLA违约升级、备件缺货和维修人员技能不匹配.
- 先对照需求和实现检查这些场景. 还没实现的能力要先补齐或明确排除, 不能把未实现的功能写成已经验收通过.
- 找朋友扮演业务用户跑一遍, 记录缺陷, 修复阻止上线的高优先级问题后重新验证.
- 写一份上线检查清单, 包括回滚方案, 在测试环境演练一次上线和回滚.

## 第十五阶段 学习培训、交接和证明项目价值

项目不是你电脑上能跑就结束了, 也不是演示完就结束了. 客户团队不用天天找你, 也能正常使用和维护, 才算真正交付.

1. 了解用户为什么不愿意用新系统, 可以学习ADKAR变更管理模型, 但重点是解决实际阻力.
2. 按角色准备使用指南、演示视频和常见问题说明.
3. 指标要能说明业务有没有变好
    - 工单处理量
    - 一次修复率
    - SLA达标率
    - 维修人员利用率
    - 平均修复时间, 也就是MTTR
4. 算收益不能只算省下来的时间, 还要考虑模型、基础设施、人工复核和维护成本.
5. 交接包要包括架构说明、运维手册、联系人和已知问题.
6. 收集用户反馈, 修正规则和知识库. 不是加一个“记忆层”就会自动变好, 反馈进入系统前也要审核和评测.

### 作业

- 写一份3页左右的IT交接文档, 包括架构总览、启动和排错方法、备份恢复、联系人和已知问题.
- 准备一份面向业务用户的使用指南, 说明什么时候相信系统、什么时候人工接管.
- 做一个业务KPI看板, 展示工单处理量、一次修复率、SLA达标率、维修人员利用率和MTTR, 写清楚每个指标的口径.
- 对比使用前后的业务指标. 如果只有模拟数据, 明确写成演示结果, 不要声称已经给客户带来了真实收益.
- 录一个10分钟的完整演示, 从业务问题讲到系统运行、异常处理、业务指标和交接方式.

## 加餐 深入学习SAP和现场服务业务

这部分不是所有FDE都需要. 如果你想做制造业、设备维护或者SAP比较重的客户, 再继续深入.

1. SAP对接方式: BAPI、OData、RFC、IDoc、SAP CPI.
2. 用SAP CPI做消息映射和路由, 了解SAP Datasphere怎样为分析和AI提供数据.
3. SAP PM和CS的基本业务: 设备、功能位置、工单、通知单、服务合同.
4. 备件管理: 物料预留、库存、领料和缺货处理.
5. SLA和维修人员排班: 响应时间、解决时间、技能、地理位置和可用时间.
6. IoT和预测性维护: 传感器数据怎样触发告警或维修流程.
7. 了解客户所在行业和地区的数据隐私、安全与合规要求, 不要照搬其他地区的规则.

### 作业

- 写一张BAPI对接目录表, 覆盖新建工单、读取设备、确认工单工序、新建服务通知和查询物料可用性这5类操作.
- 对照目标SAP版本的文档确认接口, 列清楚名称、输入、输出、错误码和权限要求, 不要让AI猜函数名.
- 选一个操作, 在获得授权的沙箱里验证. 没有环境时先做接口设计和模拟测试, 明确哪些尚未实测.

## 最后要做出来什么

学完之后, 你应该有一个能从头讲到尾的项目, 而不是一堆互不相关的教程代码.

- 一个能运行、能测试、能部署的工单系统.
- 一套能查设备手册、带出处回答的RAG.
- 一个有工具权限、人工复核和失败处理的工单Agent.
- 一层有文档、可验证的企业数据对接.
- 一套监控、评测、安全检查和回滚办法.
- 从调研、流程、需求、设计, 到验收、培训和交接的一整套材料.

工具以后会变, 模型也会变. 但把问题问清楚、把系统做稳、把结果验证出来、把东西交给客户用, 这些能力会一直用得上.
