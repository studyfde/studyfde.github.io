# 初学者FDE学习之路

## 写在前面的话

FDE现在是一个特别火的名词，说白了就是去客户现场把AI真正做出来、跑起来的人。随着AI在企业里用得越来越多，企业最缺的不再是只会聊概念的人，而是能进到业务一线、把活干出来的FDE。

对于程序员或者产品经理来说，转型FDE可能是当前最好的选择。

但是，现在的问题是市面上的很多材料都特别虚，要么全是拗口的词，要么脱离国内的真实情况，没有说到点子上。

本文就从一个初学者开始说，怎么一步一步学FDE。我们把海外最新的2026学习路线拆成了适合中国人的学习方案，不讲虚话，全用大白话告诉你每个阶段学什么、做什么作业。另外，我们还专门加了**教育专家**和**美术设计**现在最新在用的工具和方法，帮你不仅能把系统写出来，还能把知识学扎实、把界面和汇报做得漂亮。

## 面向谁

这篇文章面向对计算机编程有一定了解，并且（最好）会使用 Claude Code、Cursor 或者 Codex 的朋友。

简单来说，最好能手搓，其次是能用 AI 写出来下面的小东西：

1. Python 能写一小段代码，读文件，会写循环，会写 if、break、函数，看得懂基本的报错。
2. SQL 会对表进行增删改查，会 join 连表。做 FDE 要经常去企业数据库里拉数据、看数据。
3. Git 能拉代码、能提交，会建分支。
4. 知道网页请求和返回是怎么回事，看得懂 JSON，明白调接口是在干什么。
5. 遇到问题能看报错信息，会用打印和日志一步步找问题，会查文档，而不是只会把报错丢给 AI 瞎试。

如果你还没用 Python 操作过数据库，先照着这里做一遍：[SQLite 数据库指南：从零开始掌握 Python 数据库操作](https://blog.csdn.net/2301_80216352/article/details/155320108)。会用 Python 对 SQLite 进行增删改查即可。

> **一个很管用的学习建议**：
> 不要每学一个新阶段就推倒重来开个新项目。从第一阶段开始，我们就一直做同一个**“设备报修与工单系统”**——从最简单的增删改查开始，一步一步往上加 AI 摘要、查设备手册、自动派单、连企业系统、打包上线、加监控，最后补齐需求文档和验收材料。全部学完，你手里就有了一套能从头讲到尾的完整作品。

## 第一阶段 学习企业化使用Python

从市面上的工作需求来看，Python 是最重要的技能，也是最常被要求具备的技能。这里你需要学的是用于企业级 AI 的 Python，因为 Python 能干的事太多了，你不用去把爬虫或数据分析那套全学完。实际上，你可以每天花 2–3 个小时来持续学习。

但是，你不需要完全学透了 Python 才进入第二阶段。在有一定基础之后，就可以直接尝试用 Python + FastAPI 来搭一个 Web 服务器。

总体来说你要学习的东西包括：

1. Python 基础
   - for 循环、数据类型、变量、if else
   - 函数、类和对象、基础的异步写法
2. FastAPI
   - 接口设计（怎么定路径、怎么接参数）
   - 后台任务（慢的活放后台跑，别卡住界面）
   - 中间件
3. Pydantic
   - 确定请求和返回的数据格式
   - 自定义校验规则（比如手机号、状态不能乱填）
   - 嵌套模型
   - 报错处理
4. 环境管理：用 `.env` 文件管理不同环境的配置和密钥，密钥绝不能直接写死在代码里。
5. 在 Python 里调大模型接口：可以用国内的 DeepSeek、通义千问、智谱，或者海外的 Claude、OpenAI、Groq。

### 作业

- 用手写一个工单跟踪的 FastAPI 服务，包含 5 个接口：
  - 新建工单
  - 列出全部工单
  - 改工单状态
  - 按 ID 查工单
  - `/summarize` 接口，调大模型给工单描述做摘要
  - 用 Pydantic 模型校验请求和返回的数据，报错处理要规范（使用 `HTTPException`、返回格式统一的报错信息）
- 把项目推到 GitHub，写个 README 说清楚怎么跑起来。

## 第二阶段 学习Vibe Coding

我们要做 FDE，肯定要熟练掌握怎么用 AI 写代码。在客户现场经常只有两天时间给你搭原型，用 AI 写代码能快好几倍。但要记住：**代码出事是你负责，不是 AI 负责**。现在很多面试也会专门考你怎么挑出 AI 代码里的毛病。

1. 选一个顺手的工具用熟，建议是 Claude Code、Codex 或者 Cursor。
2. 大模型方面，经费够就选 Opus 5.5 或 Sonnet 5.5，追求性价比就用 DeepSeek 或通义千问代码模型。
3. 学习怎么用 Claude Skills、怎么写 `CLAUDE.md`、怎么管好上下文。
4. 和 AI 编程时养成好习惯，尽量拆成一步一步让 AI 来做，并且在过程中及时纠正和验证：
   1. 先做方案设计（可以让 AI 先向你多提几个问题，把需求问清楚）
   2. 让 AI 根据方案先写好测试用例
   3. 再让 AI 按计划一步步写代码
   4. 每写完一小步，立刻验证和测试
5. AI 经常出错的地方，都要自己去检查和追问：
   1. 给自己加戏，编造本来没有的需求或不存在的接口
   2. 报错处理乱写（比如报错了直接吞掉不提示）
   3. 漏掉边界情况和关键处理，或者把密钥直接写进代码里

### 作业

- 用 Claude Code、Codex 或 Cursor，给第一阶段的工单系统加功能：
  - 先写一个 `CLAUDE.md`
  - 给项目增加 5 个规范，包括命名、报错处理、文件夹结构、类型标注、不写死密钥
  - 再让 AI 加 2 个新功能：分配维修人员和带校验的任务优先级
- 检查 AI 的代码：让 AI 生成大约 100 行新功能的代码，然后不靠 AI，自己找出并修掉至少 3 个问题（比如编造的接口、漏掉的边界情况、敷衍的报错处理）。

## 第三阶段 学习大模型基础和RAG

去企业做项目，有差不多三四成的活都要查企业自己的资料：比如设备怎么修、报销有什么规定、合同里怎么写的。大模型本身没看过客户公司的文件，不能让它瞎编，得让它“先查资料、再照着回答”，这就是 RAG。

1. 了解 AI 的基本概念
   - 机器学习、深度学习、生成式 AI、Agent 分别是什么
   - Transformer 和大模型是怎么一段一段往后生成文字的
   - 学习 token、上下文窗口、temperature、top-p 等概念，知道调这些参数会让回答变稳还是变发散
2. 文档处理
   - 从 PDF、Word 制度文件、Excel 表格里把内容取出来
   - 固定长度切分、按段落递归切分、按语义切分，试试不同切法效果差在哪
   - 切的时候保留好文档名称、页码这些来源信息
3. 向量和检索
   - 搞明白向量化（embedding）是干什么的
   - 选一个向量数据库来用，比如 ChromaDB、Qdrant、Milvus 或者 pgvector
   - 了解关键词检索、向量检索、混合检索（两个一起用）和重排序；同时也要知道，不是所有查资料的活都非得用向量库
4. 回答要有依据
   - 回答必须带上出处和页码
   - 资料里找不到就直说不知道
   - 不要拿模型自己瞎编的东西去冒充企业的规章制度
5. 使用时，心里一直要算着三笔账：回答准不准、反应快不快、每次调接口花多少钱。

### 作业

- 找 10 份可以合法使用的真实 PDF，优先选设备说明书或操作手册，后面直接接到工单系统里。
- 做一个 RAG 项目：`读取文档 → 切分 → 转向量 → 检索 → 回答`，记得在答案里一定要带上文档名称和页码。
- 把代码和运行说明放到 GitHub。注意千万不要上传客户的保密文件，对外展示一律用公开数据或脱敏数据。

## 第四阶段 学习Agent、多Agent和MCP

前面的 RAG 是“你问一句，它答一句”。到了 Agent 这里，是“你交代一件事，它自己去查资料、做判断、调接口把活干完”。在客户现场，很多自动化的活都是这样跑起来的。

要学的东西包括：

1. Agent 到底是怎么干活的
   - 核心就是一个循环：先想一想 → 调工具干活 → 看返回结果 → 再想下一步怎么走
2. 工具调用
   - 给工具定清楚输入输出的格式和边界，让模型输出规整的 JSON，别让它自由发挥
3. 单 Agent 和多 Agent 系统
   - 先用 LangChain 做一个简单的 Agent 练手（比如购物助手或查单助手）
   - 再用 LangGraph 做多 Agent 配合的系统：搞清楚状态、节点、条件分支、以及记忆怎么存下来
4. 学习多模态 Agent
   - 让 Agent 能看懂现场拍过来的设备故障照片、铭牌或者扫描件
5. 人工介入把关
   - 当 Agent 自己拿不准、或者要做不能反悔的动作（比如删数据、下单采购、派紧急工单）时，必须先停下来，转给人来确认
6. MCP 协议
   - 把企业里的工具用统一的标准接给 Agent，不用每个项目都重新造一套轮子
7. 限制与测试
   - 管住 Agent 能干什么、不能干什么，上线前先测好，别等客户先发现问题

### 作业

- 在第一阶段的工单系统上，做一个**工单分派 Agent**：
  - 读进来的报修内容 → 先用第三阶段的 RAG 查设备手册 → 判断优先级 → 再通过工具调用你的接口新建工单
- 加上人工复核：如果 Agent 算出来的把握低于 85%，或者工单是最高优先级的 P1，就不要自动建单，直接转到“待人工复核”状态。
- 录一个 5 分钟演示视频，像给客户 IT 团队讲一样，说清楚 Agent 是怎么做决定的。
- 再做一个 **3 个 Agent 配合的 LangGraph 系统**（处理维修缺备件时的采购申请）：
  - 1 号 Agent 从询价单和供应商文件里提取关键字段
  - 2 号 Agent 对照批准供应商名单校验信息全不全、合不合规
  - 3 号 Agent 起草采购建议，发到一个模拟审批接口

> **在客户现场写代码的心态**：你不是在做玩具演示，你写的代码是要长期跑在客户环境里的。客户那边历史数据又乱、IT 安全规矩又多、用系统的人又不懂技术。所以代码要写得皮实，文档要写得清清楚楚。

## 第五阶段 学习对接企业系统和数据

AI 很少是凭空独立跑的，绝大多数时候都是长在企业原来的老系统上面——比如国外的 SAP、Oracle、微软 Dynamics，或者国内企业到处在用的**用友、金蝶、泛微 OA、飞书、钉钉、企业微信**。

很多 FDE 岗位干脆就叫“FDE / 对接工程师”。你的任务就是把这些系统里的数据拿出来喂给 AI，再把 AI 处理的结果写回去。

要学的东西包括：

1. 摸清企业系统的底细
   - 先搞清楚每类数据到底以哪个系统为准，分清什么是**主数据**（比如设备台账、员工名单，平时不怎么变）和**交易数据**（比如每天的报修单、领料单，天天在变）
   - 常见系统（比如 SAP、用友、金蝶）各个模块大概管什么（管设备、管客服、管库存、管人事），知道个大概就行，不用去钻得像专职顾问那么深
2. 数据怎么拿出来
   - 现成的连接器、REST 接口、OData 接口、MCP 服务，客户现场有什么就用什么
   - 不用在自己电脑上装庞大的 SAP，直接用官方免费的在线沙箱就能练调接口
3. 企业级接口的硬规矩
   - 怎么认证（OAuth2、密钥、签名）、怎么限流、失败了怎么自动重试
   - 最重要的是**防重复提交**：网络卡了重试一次，绝不能在系统里建出两张一模一样的工单
4. 面对脏数据的心理准备
   - 真实企业里到处是重复录入的设备、谁也看不懂的内部代号（得查对照表）、还有几年前的过期数据，都要先洗干净再给大模型用
5. 一项很稀缺的真本事：知道进场该向客户 IT 团队要什么
   - 数据字典、接口目录、测试账号权限、沙箱环境——这四样要不到手，后面根本没法干活

### 作业

- 去 SAP 官方的免费沙箱（`api.sap.com`）注册个账号，拿免费密钥调一下设备主数据接口（`API_EQUIPMENT`），把设备详情、安装位置和维护工厂拉回来。
- 写一个 Python FastAPI 接口把上面这个调用包一层，返回规整的 JSON（设备状态、上次维护日期、负责的维修员），再把它接成你 Agent 的一个工具。
- 写一页纸的《对接说明文档》（来源系统、接口地址、认证方式、字段对应关系、更新频率），写得像真要交给客户 IT 部门审核那样。

## 第六阶段 学习部署上线：Docker、K8s和CI/CD

代码在你自己的电脑上能跑，不等于在客户那里能用。做 FDE，你还得负责把东西打包、部署出去，并且做到改完代码能自动测试、自动更新。

要学的东西包括：

1. Docker
   - 会写 Dockerfile，会用多阶段构建把镜像体积缩小，会推到镜像仓库（阿里云、腾讯云、AWS 或者 Docker Hub）
2. Kubernetes（K8s）
   - 不用背全套原理，但要看得懂配置文件，知道部署、服务、配置项、密钥、内存和 CPU 上限、健康检查探针是怎么回事，能把服务跑起来
3. 用 GitHub Actions 做自动流水线（CI/CD）
   - 代码一推上去，自动走完：检查代码 → 跑测试 → 打包镜像 → 推送 → 自动部署
4. 接口网关与密钥安全
   - 了解网关上的限流、登录认证、跨域和路由
   - 生产环境的密钥要放进专门管密钥的服务里，别明文写在代码或普通配置里
   - 了解换新模型时的灰度放量（先放一小部分流量试试水）
5. 重点了解：**客户内网私有化部署**
   - 国内很多国企、银行、大厂房要求数据绝对不能出他们自家的机房。你要知道怎么在断网环境里用离线镜像仓库、怎么用 Rancher 管集群，以及怎么用 **Ollama 或 vLLM** 在客户的本地显卡服务器上把开源大模型跑起来。

### 作业

- 把前面做的多 Agent 工单系统用 Docker 打包，推到镜像仓库。
- 写一个 GitHub Actions 工作流，代码推到主分支就自动跑测试、自动部署。
- 把它部署到一台云主机或云容器服务上，跑通完整的流程，给出一个能打开访问的链接。

## 第七阶段 学习LLMOps：上线之后看住系统

系统部署上线只是第一步。真正难的是上线之后：真人在用、模型天天在扣钱、偶尔还会抽风答错。这一阶段学的是怎么看着它、测着它、管住它。

要学的东西包括：

1. 调用链路日志
   - 接上 **LangFuse**（开源，能装在客户内网，国内最常用）或 **LangSmith**
   - 每次请求都记下来：输入了什么、查到了什么、输出了什么、哪步花了多少秒、用了多少 token
2. 用 Prometheus + Grafana 做监控看板
   - 先把 4 个最核心的数字看住：**每分钟请求数、95% 用户的响应耗时（P95 延迟）、报错率、每天花掉的 token 钱**
3. 上线后的持续评测
   - 准备一套固定的测试题（回归测试集），每次改了提示词或换了模型都跑一遍，看看瞎编率有没有变高、跟标准答案比差多少
4. 管住成本
   - 设好每天的预算上限和超额报警
   - **大小模型搭配用**：简单的分类、抽字段走便宜的小模型；只有真需要动脑子综合判断的地方，才调贵的模型
5. 安全与权限
   - 知道大模型常见的安全漏洞：比如被人用话术套出系统提示词、泄露敏感数据、输出危险内容，知道怎么在代码里防住
   - 多部门共用一套系统时，把权限分清楚，懂得怎么对接企业单点登录（比如飞书、钉钉、企微登录或公司域账号）
6. 压测与稳定性
   - 上线前先用 **Locust** 做压力测试，试出系统同时进来多少人会卡，定好服务保障指标。

### 作业

- 给你的 Agent 接上 LangFuse 或 LangSmith，抓 50 条不同类型工单的真实调用记录。
- 搭一个 Grafana 看板，把上面说的 4 个核心数字展示出来。
- 给你的系统写一份《安全风险排查表》：找出 3 个可能被人用恶意话术攻破的地方，写清楚怎么防。
- 用 Locust 模拟 50 个用户同时访问你的接口，把压测结果记下来。

## 第八阶段 学习企业AI系统设计（HLD和LLD）

调通一个大模型接口只要十分钟，但围着模型搭一套**又快、又省钱、又稳当、出了问题还不丢人**的系统，才是真本事。这也是 FDE 面试最喜欢一上来就问的。

要学的东西包括：

1. 先搞懂客户现在的系统是怎么搭的，你新加的东西千万别把人家原来的正常业务搞坏了。
2. 明白 AI 系统为什么跟传统软件不一样：
   - 大模型天生有四个毛病：**每次回答不一样、贵、慢、还会一本正经地胡说八道**。你在架构里加的每一个设计，都是为了治这四个毛病里的某一个。
3. 模型层怎么选：
   - 调现成接口还是自己部署？怎么让小模型干粗活、大模型干细活？这是省钱最大的一招。
4. 检索层怎么查：
   - 存文档和查文档是两条路。记住一句话：**RAG 答得不好，十次里有八次是检索没找对资料**，先查切块和检索，别上来就怪模型笨。
5. 流程怎么串：
   - 算一笔简单的账：就算每一步有 95% 的把握，连着走 10 步，最后整件事办成的概率也只剩 60% 左右。所以企业里规矩固定的事，优先写死成固定流程；只有真正需要随机应变的活，才交给开放的 Agent 去跑。
6. 怎么既快又省钱：
   - 用流式输出让字先蹦出来；做好缓存（一模一样的问题直接回、意思相近的问题查缓存、固定的提示词前缀也缓存起来）；限制最大输出字数。省钱是设计出来的，不是月底看账单才发现的。
7. 怎么兜底：
   - 主模型挂了自动切备用模型，备用模型也不行就体面地提示用户并转人工处理，千万别悄悄失败卡死在那里。
8. 写好两份核心设计图：
   - **高层设计（HLD）**：画清楚系统有哪几块、怎么配合、为什么选这套技术、部署在云上还是内网、怎么连企业老系统。
   - **详细设计（LLD）**：把每个接口的参数、数据库每张表、Agent 和工具的边界、每个危险动作前的拦截关卡都定死；画时序图时，**不光要画顺利走通的图，还要画出写入失败时怎么处理的图**。
   - 把重要的技术选型理由记下来，画图用 `draw.io`、`Eraser.io` 或 `Mermaid`，记得把图的源文件留好，别只留一张截图。

### 作业

- 给你的工单系统写一份高层设计（HLD）：包含架构图、模块清单、技术选型理由、部署方式、大小模型分配策略，以及一页“模型到底调接口还是本地部署”的决策说明。
- 给同一个系统写一份详细设计（LLD）：至少 8 个接口的明细表、数据库表结构（设备、工单、维修员、超时规则）、新建工单的时序图，再画一张**往企业老系统写数据失败时怎么处理的时序图**。
- 对着你的图，录一段 5 分钟的讲解视频，就像在面试一样把它讲清楚，自己回看一遍顺不顺。

## 第九阶段 先找到真问题，再动手（用户调研）

前面八个阶段学的都是“怎么把东西做出来”。从这里开始，学的是去客户现场“怎么搞清楚到底该做什么”。

原路线打了个特别好的比方：**好 FDE 就像个沉稳的老医生**。病人进门说头疼，老医生不会抓起止疼药就开，而是先问、先查。最后发现其实是胃胀气引起的头疼，治好胃，头自然就不疼了。做企业 AI 也一样，客户嘴上说“给我做个聊天机器人”，你得先帮他找到业务里真正的卡点，再动手写代码。

要学的东西包括：

1. 连问 5 个为什么（5 Whys）：顺着表面的抱怨一层层往下刨，找到真正的病根。
2. 学会怎么提问（参考《妈妈测试》）：
   - 别问“我给你做个 AI 自动派单好不好？”（对方客气一下肯定说好），要问开放式问题：“你昨天是怎么派单的？哪一步最费时间？上次出错是什么时候、惹了什么麻烦？”
3. 现场跟岗：
   - 搬个凳子坐到一线员工旁边，亲眼看他怎么打开表格、怎么在群里发消息、怎么敲键盘，把他现在的每一步手工活都记下来。
4. 分清两拨人的不同心思：
   - 掏钱的老板想要什么（省钱、看报表、不出事），和天天用系统的一线员工想要什么（少填表、别卡顿、别背锅），往往不是一回事，两边都要听。
5. 调研前先要齐材料：现有的操作规章、部门架构图、现在的考核指标，没有这些去聊就是空聊。
6. 把痛点算成具体的账：
   - 手工干花了多少小时？出错率是多少？超时被罚了多少钱？算不出数字，后面就说不清楚这事值不值得做。
7. 管住需求边界，签好保密协议，守好客户现场的数据规矩。

### 作业

- 挑一个你真能接触到的业务流程（公司里的报修、门店进货、或者家里生意的流程都行），写一份包含 10 个开放式问题的访谈提纲。
- 真去找一个天天干这活的人聊一聊、看一看，记下他现在的步骤和痛点，算出三个数：**手工花了多少小时、出错率多少、每次出错损失多少钱**。
- 写一页纸的《问题说明》，把业务影响算清楚，拿给那位受访者看一眼，让他确认写得准不准。

## 第十阶段 把现在的流程画出来（泳道图）

动手写自动化代码之前，先把人家现在的干活流程画成一张图。**这张图就是你和客户对“现在到底是怎么干活的”达成的一致意见**。

要学的东西包括：

1. 泳道图的基本画法：
   - 每个岗位或每个系统占一条横道，把开始、结束、具体任务、判断分支和连线画清楚。
2. 先画现状图（AS-IS）：
   - 现在实际是怎么干的就怎么画，哪怕是“抄在纸上再拍照发微信”这种手工步骤，也一步都别漏。
3. 挑出适合用 AI 自动化的步骤：
   - 优先找那些**重复的、有规矩可循的、量大的、人容易看花眼出错的**地方。
4. 再跟客户一起画出改造后的未来流程图（TO-BE）：
   - 标清楚哪一步让 AI 自动跑，哪一步由人来点确认，AI 卡住了往哪退。
5. 工具选一个顺手的就行：`draw.io`、飞书画板、`Miro` 或者 `Eraser.io`。

### 作业

- 给上一阶段调研的流程，画一张完整的现状（AS-IS）泳道图。
- 把你打算用 AI 自动化的步骤涂成醒目的橙色，在旁边写清楚为什么挑这几步。
- 再画一张改造后的目标（TO-BE）泳道图，拿给懂这个流程的人看一眼，确认没漏掉关键步骤。

## 第十一阶段 把需求写清楚（写BRD）

正规的企业客户，在看你写的代码之前，先看你写的文档靠不靠谱。需求文档写得稀里糊涂，代码写得再漂亮也要返工。

要学的东西包括：

1. 业务需求文档（BRD）的 8 个核心部分：
   - 项目背景摘要、**这次做什么和明确不做什么**、现状与改造后流程、功能需求表、系统对接需求、数据需求、验收标准、风险和前提假设。
2. 验收标准必须能拿尺子量：
   - 别写“系统要快、回答要准”，要写“工单分派在 95% 的情况下不超过 5 秒”、“标准测试集上的页码引用准确率达到 90% 以上”。
3. 把“不做什么”写进文档：
   - 哪些功能这次不做、为什么不做（比如放到二期），白纸黑字写清楚，防扯皮。
4. 管好文档版本：每次改需求都记下改了哪、谁提的、时间怎么顺延。
5. 避开三个最要命的坑：需求话说两头、漏写排除项、验收标准没法测。

### 作业

- 给你调研的那个流程（或者我们的工单系统）写一份完整的 BRD 文档，包含上面说的 8 个部分，其中功能需求表里至少列 10 条具体需求。
- 找个同行或朋友帮你看一遍：检查每条需求后面有没有能直接拿来测的验收标准？

---

## 第十二阶段 告诉开发具体怎么做（写TDD）

如果说上一阶段的 BRD 讲的是“要什么、为什么做”，那么这一阶段的**技术设计文档（TDD）**就是告诉写代码的人（或者写代码的 AI），系统在每个细节上到底该怎么表现。

要学的东西包括：

1. 怎么从业务需求一步步推出功能流程和数据流向。
2. 字段级的校验规矩：哪些项必填、格式长什么样、最大最小允许填多少。
3. 把业务规则写死、写透：
   - 比如工单超时升级规则：从建单开始计时，到了规定时间的 80% 先发消息提醒，到了 100% 自动往上升一级。
4. 出错和异常情况怎么处理：缺了字段、接口超时、模型返回乱码时，系统每一步该干什么。
5. 对接明细：来源系统、接口路径、认证方式、字段对应表、多久同步一次。

### 作业

- 从你前面写的 BRD 推出一份完整的 TDD：功能流程、字段校验、异常处理、对接明细都要有。
- 挑一条具体的业务规则（比如超时自动升级），画出流程图并配上规则表，写得像真要直接交接给开发写代码一样。
- **真刀真枪检验一下**：把你写的这份规则说明直接喂给 Claude Code 或 Codex，看 AI 能不能不靠猜、一次性把代码写对。如果 AI 写错了，说明你的文档还没写清楚，改好文档再试。

---

## 第十三阶段 跟客户打交道与向上汇报

技术能帮你进场，但跟人打交道的本事，才决定你能不能在客户现场把事办成。

要学的东西包括：

1. 先认清客户那边的四拨人：
   - 天天用系统的一线员工、管流程的部门领导、管安全和服务器的 IT 把关人、还有最后掏钱的大老板。按“谁说话算话”和“谁最关心这事”把他们理清楚。
2. 怎么管住对方的预期：
   - 学会客气但坚定地说“不”，学会拿功能范围换交付时间（“加这个可以，那另一个功能我们放到下个月做”），所有嘴上谈好的事都要落到文字上。
3. 保持固定的沟通节奏：
   - 会前有议程、会后有纪要、每周有进展汇报、遇到解决不了的事知道找谁升级。
4. 给大老板汇报的“三页幻灯片”法则：
   - 老板不想听技术细节。就三页：**第一页讲现在有什么痛点、亏了多少钱；第二页讲我们的方案怎么解决；第三页讲做完之后省了多少时间、带来了什么结果**。
5. 给不懂技术的人演示：
   - 只展示业务结果，别展示代码和架构图。而且客户内部平时习惯说什么行话或方言，要能听懂、能接上话。
6. 遇到不确定的地方别硬撑，大大方方问清楚：“帮我确认一下，您刚才说的意思是 X 还是 Y？”

### 作业

- 写一篇 300 字的小短文：《FDE 能解决什么传统售前工程师解决不了的问题？》
- 做一份只有 3 页幻灯片的高管汇报（问题、方案、结果），录一个 5 分钟的汇报视频，讲清楚你前面做的工单项目。
- 找个朋友扮演“总想加需求、又难缠的业务领导”，开一次模拟沟通会，练练怎么顶住不合理加塞，会后写一份会议纪要。

## 第十四阶段 带客户验收（UAT）与正式上线

自己测通过不算数，**客户那边真正干活的人坐下来试过、点头说能用，才算验收通过**。上线就是证明你的系统真能扛事的地方。

要学的东西包括：

1. 搞明白开发自测和客户验收（UAT）的区别：自测看的是代码对不对，客户验收看的是业务上好不好用。
2. 写验收测试表：把测试场景、前提条件、操作步骤、预期结果、实际结果、通没通过，一列列写清楚。
3. 定好验收的开始和结束标准：满足什么条件才能请客户来测，测到什么程度才算合格能上线。
4. 带着真实用户做验收：把发现的问题按轻重缓急分好类（致命、高、中、低），先修卡脖子的大问题。
5. 上线检查清单：历史数据核对过没有、出事了怎么一键退回旧版本（回滚方案）、值班联系人列好没有。
6. 上线后的重点看护期：刚上线那几天最容易出事，先定好出问题找谁、怎么响应。

### 作业

- 给工单系统写一份包含 **15 个业务场景的验收测试表**，覆盖最高优紧急派单、超时升级、备件缺货、维修员技能不匹配这些情况。
- 找个朋友扮演“业务调度员”，照着表真跑一遍，记下挑出来的毛病，先把最严重的问题修掉。
- 给你的项目写一份《上线检查清单》，里面必须带上出事怎么退回旧版本的回滚方案。

## 第十五阶段 培训、交接与算清项目收益

记住一句话：**项目不是在系统跑通那天结束的，是客户团队不用你帮忙、自己也能天天顺畅用起来，才算真干完了**。

要学的东西包括：

1. 明白一线员工为什么一开始不乐意用 AI 系统：
   - 怕麻烦、怕改变习惯、怕点错了背锅、甚至怕被机器抢了饭碗。先理解人家的顾虑，把系统做成帮他们减轻负担的工具，再推下去。
2. 培训材料要按岗位分开做：
   - 不同岗位看不同的操作指南、不同的演示短视频（3 分钟录屏远比 10 页文字管用），常见问题解答也要写得通俗。
3. 算清项目的实际收益（ROI）：
   - 围绕客户看得懂的业务指标来算：处理了多少单、一次修好率高了多少、超时违约少了多少、人员利用率、平均修好一台设备快了多少。
4. 做一张让外行领导也能一眼看懂、信得过的业务看板。
5. 留下一套完整的交接资料包：架构总览图、日常维护与排错手册、联系人表、目前已知的小问题。
6. 上线后定期回头复盘，收集用户的反馈，让系统越用越顺。

### 作业

- 写一份 3 页纸的《IT 交接文档》：包含架构总览、日常运维与重启排错办法、联系人表、已知问题。
- 做一个业务效果看板，至少展示：处理工单数、一次修复率、按时达标率、维修人员利用率、平均修复时间。
- 录一个 **10 分钟的完整项目演示视频**，就像给客户大老板做总结汇报一样，把从发现问题到系统上线、再到收益看板的整套成果讲一遍。

## 加餐：深入SAP对接与制造业现场服务（按需选学）

> 这部分不是所有 FDE 岗位都需要。但如果你打算去大型制造业、工厂设备维护，或者去 SAP 用得特别重的咨询公司，把这块摸透就是很大的加分项。

要了解的东西：

1. SAP 常见的几种对接方式：BAPI、OData、RFC、IDoc、以及做消息转换的中间件 SAP CPI 和供 AI 读数据的 SAP Datasphere。
2. 制造业与现场服务的核心业务：
   - 工厂维护模块（管设备台账、安装位置、维修工单、报修通知单）
   - 客户服务模块（管服务单、服务合同、按工时与备件算钱）
   - 备件管理（预留物料、发料出库、查库存）
   - 超时考核（响应时间与解决时间的区别、P1–P4 优先级、违约罚款）
   - 维修员排班（按技能派、按距离远近派、看排班日历）
   - 物联网预警：设备上的传感器（测振动、温度、压力）发现异常后，怎么自动触发维修工单。

### 选做作业

- 写一张《SAP 现场服务自动化接口目录表》，列出 5 个常用操作（新建工单、读设备信息、确认工单工序、新建服务通知、查备件库存）对应的函数名、输入输出参数和错误码。

## 跨界武器库：教育专家与美术设计师都在用的最新工具

很多程序员代码写得很溜，但一到客户现场做调研、画架构图、搭界面、做汇报或者给员工做培训就吃亏。原因很简单：缺了**教育专家（怎么把复杂的事讲明白、让人快速学会）**和**美术设计（怎么把图和界面做得干净好看、让人一眼信服）**的看家工具。

把下面这两套最新的专业工具用起来，你的交付质量会比普通工程师高出一大截：

### 一、 教育专家（快速吃透陌生行业与培训客户）的最新工具与方法

做 FDE，前三天要自己快速搞懂客户的陌生行业，最后三天要把不懂技术的客户教会，这全都是教育学最擅长的事。

| 方法或工具 | 大白话讲明白核心用法 | 在 FDE 项目里怎么用它偷懒提效 |
| :--- | :--- | :--- |
| **费曼学习法 + NotebookLM** | 能不能用大白话给外行讲懂，是检验你真懂假懂的唯一标准。Google 的 **NotebookLM** 是现在啃陌生资料最强的神器。 | 进陌生客户现场前，把客户几百页的设备手册、行业规章全丢进 NotebookLM，让它自动整理出常见问题、知识脉络，甚至生成一段两个人的对谈音频，坐地铁听完就能去跟客户聊业务。 |
| **搭梯子教学法** | 教人用新工具不能一上来就扔一本厚说明书，要先给现成的半成品模板，让人先尝到甜头。 | 第十五阶段给客户员工做培训时，先在系统里预设好 5 个“点一下就能出结果”的常用按钮和模板，等大家用顺手了，再教怎么自己写提示词。 |
| **知识串联与防遗忘（Obsidian + Anki）** | 零散收藏的文章过两天就忘光了，要把踩过的坑连成自己的知识网。 | 用 **Obsidian** 或 **飞书知识库** 记下每次调接口、调提示词踩过的坑；把面试常问的系统设计套路做成 **Anki** 小卡片，每天花 10 分钟翻一翻。 |
| **高颜值微课录屏（Screen Studio / Loom / 剪映）** | 没人爱看几十页的操作文档，一段 3 分钟、鼠标点哪镜头就自动放大哪的高清录屏，谁都能看懂。 | 交每个阶段的作业，或者给客户录系统操作指南时，用 **Screen Studio**（镜头会自动平滑跟着鼠标走）或 **剪映** 录 3 分钟短视频，自动加上字幕，专业感拉满。 |
| **一键生成汇报幻灯片（Gamma / Marp）** | 别把时间浪费在调文本框对齐上，先把逻辑写清楚，排版交给 AI。 | 写完需求文档或项目总结后，直接把 Markdown 文字丢进 **Gamma.app**，一分钟生成排版干净、带图表卡片的汇报幻灯片，彻底治好“程序员做 PPT 难看”的毛病。 |

### 二、 美术设计与视觉传达（画架构图、做界面与数据看板）的最新工具与方法

企业客户花大价钱买系统，**你的流程图清不清楚、界面干不干净，直接决定了客户第一眼觉得你“专不专业、靠不靠谱”**。

| 设计领域或工具 | 美术设计师的排版秘诀与最新工具 | 在 FDE 开发与汇报里怎么直接用 |
| :--- | :--- | :--- |
| **架构图与泳道图设计（Eraser.io / Excalidraw / draw.io）** | 好图就一条规矩：**主次分明**。主流程线加粗、异常报错画虚线、核心 AI 模块标亮色，整张图颜色别超过 3 种。 | 平时写设计文档用 **Eraser.io** 或 **Mermaid**（直接用文字生成规范的架构图，方便改）；在客户现场边聊边画用 **Excalidraw**（手绘风，客户不紧张）；正式交差用 **draw.io**。 |
| **现代企业后台界面（shadcn/ui + Tailwind + v0.dev / Lovable）** | 别再用十年前那种满屏刺眼蓝色的老旧后台了。现在最好看的工业级设计讲究**留白、对齐、统一的圆角和干净的灰白配色**。 | 做工单系统前端页面和看板时，直接让 **v0.dev**、**Lovable** 或 Claude 按照 **Tailwind CSS + shadcn/ui** 的风格生成页面代码，做出来的界面直接就是硅谷一线大厂的质感。 |
| **先画草图再写代码（Figma / MasterGo / 即时设计）** | 改一张界面草图只要 5 分钟，写完代码再推翻重改要两天。 | 在第十一阶段跟客户定需求时，用 **Figma**（或者国内好用的 **MasterGo / 即时设计**）花半小时拖出个工单界面草图，让客户看一眼确认“就是长这样”，再开始写代码。 |
| **让老板一眼看懂的数据看板（ECharts / AntV）** | 数据看板铁律：**最上面一排永远先放大字号的结论数字（比如省了多少钱、达标率多少），下面再放趋势折线图**；红绿颜色只用来标报警和达标。 | 第七阶段做系统监控、第十五阶段给老板做收益看板时，用 **Apache ECharts** 或蚂蚁的 **AntV**，套用干净的商务配色，让不懂技术的老板 3 秒钟看清项目价值。 |
| **多模型混搭生成配图（ChatGPT 画图 / 即梦 / Midjourney）** | 汇报材料里的流程图、示意图风格要统一，别东拼西凑。 | 原路线特别提醒了一条经验：如果让 Claude 画图总画歪，别跟它死磕，立刻换 **ChatGPT 的画图功能**或者国内的 **即梦** 来生成架构示意图和汇报配图，哪个模型干哪件事顺手就用哪个。 |

## 优秀FDE的12条实战心法

原版路线图采访了几位在一线摸爬滚打多年的资深 FDE，总结了 12 条在客户现场不翻车的黄金经验：

1. **说客户听得懂的人话**：沟通好不是指飙专业词汇。如果客户车间里平时讲方言或行业土话，你要能听懂、能接上茬，不然你连人家的真需求都摸不着。
2. **到什么山头唱什么歌**：每个客户的公司脾气、老旧系统、审批规矩都不一样。在上一家好使的办法，换一家可能就碰壁，要能跟着现场环境随时调整。
3. **习惯用 AI 给自己提效**：熟练混着用 Claude、ChatGPT、Gemini、Cursor、Eraser.io。客户不在乎代码是不是你一个个字母敲出来的，只在乎你能不能按时交出好用的东西。
4. **遇到不懂的别露怯，大大方方问清楚**：聊需求时听到陌生的词，别心虚，用沉稳的语气问：“为了咱们两边理解一致，您说的这个是指情况 A 还是情况 B？”散会后回酒店赶紧用大模型补课。
5. **天下武功，唯快不破**：企业客户有各种死线和检查节点。能在开完会 **48 小时内拿出一个粗糙但真能点、真能跑的样品**，永远比憋两个星期交出一份华丽的 PPT 管用。
6. **帮客户省钱才是你的硬本事**：简单的分类和抽信息一律用便宜的小模型，只有真要复杂分析的地方才调贵的大模型。大家都能做出差不多的功能时，谁跑起来更省钱，客户就选谁。
7. **把常改的规矩做成可配置的，别写死在代码里**：客户天天改主意。如果你把业务规则全写死在代码里，客户每改一句话你都得改代码重新发版。尽量做成后台能改的配置表或自然语言规则，让客户自己就能调。
8. **给系统留个“记性”**：你不可能一辈子守在客户公司帮他们修回答。系统得能记下用户的点踩和人工改过来的正确结果，审核之后自动补进知识库，越用越准。
9. **必须懂怎么装在客户自己的机房里**：“这东西能不能装在我们自己内网服务器上？”是大客户最爱问的一句话。一定要懂 Docker 离线打包、K8s，以及怎么用 Ollama、vLLM 在内网跑开源模型。
10. **脑子里要有数据安全和合规这根弦**：懂基本的数据隐私保护、操作留痕、权限隔离。只有懂这些，去跟客户的法务和信息安全部门开会时才不会卡壳。
11. **摸清企业老系统的家底**：你不用考个 ERP 顾问证，但必须清楚客户的数据存在哪、哪个系统说了算、怎么通过连接器或接口把数据稳稳当当地拿出来。
12. **把普通员工教会才算真正完工**：最后天天用你系统的是人事、采购、财务和车间维修工。耐心地做好培训，留下带图的简单说明和 3 分钟演示视频，让他们明白“什么时候信 AI、什么时候转人工、出问题找谁”。

## 附：3个真实的企业级FDE案例参考

学完上面所有阶段后，你可以对照下面这 3 个真实的落地案例，看看一个完整的企业项目从头到尾包含哪些东西：

1. **AI 现场设备报修与派单指挥中心（也就是咱们一路做的工单系统）**
   - **解决什么痛点**：以前报修靠人工打电话分派太慢、老师傅经验新员工不会、经常到了现场才发现没备件白跑一趟，导致超时被罚。
   - **用了哪些技术**：LangGraph 多 Agent 配合 + 大小模型搭配 + 设备手册 RAG 问答 + 对接企业设备接口 + 数据库 + 实时监控看板。
   - **交付了哪些文档**：业务需求文档（BRD）、技术设计文档（TDD）、系统架构图、接口对接表、15 个场景的验收测试表、运维交接手册。
2. **工厂设备预测性维护 AI 助手**
   - **解决什么痛点**：工厂里的大机器一旦突然坏掉停产，损失惨重；机器上的传感器每天都在报数据，但没人看得过来。
   - **用了哪些技术**：传感器数据接入（测振动、温度、压力异常）+ FastAPI + LangGraph 自动判断风险 + 在机器坏掉之前自动调企业系统生成检修工单 + LangFuse 全程监控。
   - **交付了哪些文档**：传感器数据接入说明、异常判断规则表、系统对接目录、设备平均修复时间与停机率下降的效果看板。
3. **企业合同审查与提醒 AI 助手**
   - **解决什么痛点**：法务和采购每天要看成百上千页的供应商合同，人工看很容易漏掉霸王条款、违约罚款和续签截止日期。
   - **用了哪些技术**：PDF 文档解析 + 向量与关键词混合检索 + 自动提取关键条款的 Agent + 风险条款高亮提醒 + 自动化准确率评测集。
   - **交付了哪些文档**：条款提取提示词模板库、准确率测试报告、部门权限隔离方案、业务人员傻瓜操作指南。
